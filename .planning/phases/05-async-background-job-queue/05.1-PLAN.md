# Plan 5.1: Migration DB — SceneSnapshot com errorCount e production_states formal

## Goal
A tabela `production_states` existe formalmente em migrations com `CREATE TABLE IF NOT EXISTS` completo, e a interface TypeScript `SceneSnapshot` possui o campo `errorCount` necessário para o worker de retry.

## Context
A tabela `production_states` foi criada diretamente no dashboard do Supabase — ela não existe em nenhum arquivo `.sql` de migration. Se o banco for recriado ou provisionado do zero, a tabela não existirá. Além disso, a interface `SceneSnapshot` em `useProductionState.ts` não tem o campo `errorCount: number`, que é necessário para que o worker (Plan 5.2) saiba quantas tentativas já ocorreram e decida quando marcar uma cena como `fatal_error` (após 3 falhas consecutivas).

Esta migration é o fundamento de todos os outros plans. Plans 5.2 e 5.4 dependem de `errorCount` estar na interface.

**Dependências:** Nenhuma — este é o primeiro plan.

## Tasks

### Task 1: Criar migration SQL defensiva para `production_states`

**Arquivo:** `supabase/migrations/20260412000000_async_scene_queue.sql`

Criar o arquivo com o seguinte conteúdo exato:

```sql
-- Migration: async_scene_queue
-- Formaliza a tabela production_states (criada manualmente no dashboard)
-- e garante compatibilidade com o worker de background da Phase 5.

-- 1. Criar tabela se não existir (idempotente)
CREATE TABLE IF NOT EXISTS public.production_states (
  id            UUID        DEFAULT gen_random_uuid() PRIMARY KEY,
  channel_id    UUID        UNIQUE REFERENCES public.channels(id) ON DELETE CASCADE,
  user_id       UUID        REFERENCES auth.users(id) ON DELETE CASCADE,
  step          NUMERIC     DEFAULT 1,
  status        TEXT        DEFAULT 'idle',
  data          JSONB       DEFAULT '{}',
  scenes        JSONB       DEFAULT '[]',
  total_scenes  INTEGER     DEFAULT 0,
  completed_scenes INTEGER  DEFAULT 0,
  updated_at    TIMESTAMPTZ DEFAULT now()
);

-- 2. Habilitar RLS (se ainda não estiver habilitado)
ALTER TABLE public.production_states ENABLE ROW LEVEL SECURITY;

-- 3. Criar policy RLS se não existir
DO $$ BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM pg_policies
    WHERE tablename = 'production_states'
      AND schemaname = 'public'
      AND policyname = 'production_states_owner'
  ) THEN
    EXECUTE '
      CREATE POLICY production_states_owner
        ON public.production_states
        FOR ALL
        USING (auth.uid() = user_id)
        WITH CHECK (auth.uid() = user_id)
    ';
  END IF;
END $$;

-- 4. Index por channel_id para performance (se não existir)
CREATE INDEX IF NOT EXISTS idx_production_states_channel_id
  ON public.production_states(channel_id);

-- 5. Trigger para atualizar updated_at automaticamente
CREATE OR REPLACE FUNCTION public.update_production_states_timestamp()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_production_states_updated_at ON public.production_states;
CREATE TRIGGER trg_production_states_updated_at
  BEFORE UPDATE ON public.production_states
  FOR EACH ROW EXECUTE FUNCTION public.update_production_states_timestamp();

-- Nota: O campo errorCount por cena vive dentro do JSONB scenes[].errorCount
-- (campo opcional — worker trata ausência como 0, sem necessidade de ALTER TABLE)
```

**Por que não adicionar coluna `errorCount` via ALTER TABLE:** O campo `errorCount` vive dentro do JSONB `scenes[]` como propriedade de cada `SceneSnapshot`. O JSONB é schemaless — não é necessário alterar a coluna. Apenas a interface TypeScript precisa ser atualizada (Task 2).

**Verificação:** Executar `npx supabase db push` — deve concluir sem erros. Se a tabela já existe no banco de produção, todos os `IF NOT EXISTS` garantem idempotência.

### Task 2: Adicionar `errorCount` na interface `SceneSnapshot`

**Arquivo:** `src/hooks/useProductionState.ts`

Alterar a interface `SceneSnapshot` (linha 9 atual) para adicionar o campo `errorCount`:

```typescript
// ANTES (linha 9-18):
export interface SceneSnapshot {
  chapterIndex: number;
  sceneIndex: number;
  status: "pending" | "audio_done" | "visual_done" | "complete" | "error";
  audioUrl?: string;
  imageUrl?: string;
  durationSec?: number;
  prompt?: string;
  errorMessage?: string;
}

// DEPOIS:
export interface SceneSnapshot {
  chapterIndex: number;
  sceneIndex: number;
  status: "pending" | "processing" | "audio_done" | "visual_done" | "complete" | "error";
  audioUrl?: string;
  imageUrl?: string;
  durationSec?: number;
  prompt?: string;
  errorMessage?: string;
  errorCount?: number;  // Número de tentativas falhas — worker usa para retry logic (max 3)
}
```

**Mudanças exatas:**
1. Adicionar `"processing"` no union type de `status` — necessário para o worker marcar cenas que estão sendo processadas ativamente (evita race condition multi-tab)
2. Adicionar `errorCount?: number` como campo opcional ao final da interface

**O campo é opcional (`?`)** para garantir backward compatibility: cenas já salvas no banco sem `errorCount` são tratadas pelo worker como `errorCount = 0`.

**Verificação:** `npx tsc --noEmit` deve passar sem erros de tipo relacionados a `SceneSnapshot`.

## Risks

| Risco | Probabilidade | Mitigação |
|-------|---------------|-----------|
| `production_states` já existe com colunas diferentes | Média | `CREATE TABLE IF NOT EXISTS` + `ADD COLUMN IF NOT EXISTS` cobrem isso; tabela existente não é tocada |
| `channels` table não existe (FK quebra) | Baixa | Se ocorrer, remover a REFERENCE e criar sem FK; reportar ao owner |
| `npx supabase db push` rejeita o script por erro de sintaxe | Baixa | Testar localmente com `npx supabase db diff` antes de push |
| Código existente passa `status: "visual_done"` onde agora `"processing"` também é válido | Nenhum | Adição de union type não quebra código existente |
