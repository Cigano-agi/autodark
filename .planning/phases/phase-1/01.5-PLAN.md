# Plan 1.5: Corrigir useProductionState + storage.ts — Estado e Upload

## Goal
`useProductionState` não sobrescreve estado anterior em chamadas consecutivas rápidas, distingue "banco vazio" de "falha ao carregar", e `uploadToStorage` não descarta áudios legítimos abaixo do threshold atual.

## Bugs Fixed
- **BUG-013** [high] — `save` usa closure stale de `state`; chamadas consecutivas (step 2 → 2.5) sobrescrevem dados da chamada anterior
- **BUG-014** [medium] — Falha no fetch inicial do banco reseta o estado para INITIAL — usuário perde visualmente 90% de progresso durante instabilidade do Supabase
- **BUG-015** [medium] — `uploadToStorage` descarta blobs menores que 100 bytes silenciosamente — áudios de cenas curtíssimas são perdidos
- **BUG-006** [medium] — `allScenes` é persistido com `durationSec: undefined` antes da narração, corrompendo o cálculo de duração do vídeo no worker

## Context

### BUG-013 — Closure stale em save()
`useProductionState.ts:100-117`: `save` é criado com `useCallback` e captura `state` do momento do render. Se o orchestrator chama `saveProductionState(2, ...)` e imediatamente depois `saveProductionState(2.5, ...)`, a segunda chamada usa `state` do render anterior (antes da primeira chamada atualizar o React state). A segunda sobrescreve a primeira com `data` vazio.

Solução pragmática: usar um `useRef` que aponta sempre para o state mais recente, em vez de `state` diretamente no closure.

### BUG-014 — Erro de rede reseta progresso visual
`useProductionState.ts:68-71`: `if (data && !error) { setState(data) } else { setState({ channel_id, ...INITIAL }) }`. Quando há erro de rede (supabase down, RLS bloqueando), cai no `else` e inicializa o estado como se fosse a primeira execução. O usuário a 90% vê a UI como "idle".

### BUG-015 — Threshold de blob muito alto
`storage.ts:13`: `if (!blob || blob.size < 100) return null`. Cenas curtas (1-2 palavras) podem gerar áudio MP3 de 50-80 bytes. O threshold de 100 bytes descarta esses áudios válidos.

### BUG-006 — durationSec undefined persiste antes da narração
`pipelineOrchestrator.ts:240-253`: `allScenes` é construído com `durationSec: scene.durationSec` — mas nesse ponto as cenas acabaram de ser criadas por `extractScenes` e nunca passaram pelo `narratorAgent`. O campo `durationSec` é `undefined` para todas. O `saveScene` persiste `durationSec: undefined` no banco. O worker usa esse valor para calcular duração, podendo gerar NaN.

## Tasks

### Task 1: Corrigir closure stale em save() usando stateRef (BUG-013)

**Arquivo:** `src/hooks/useProductionState.ts`

**Localização:** linhas 51-117

Adicionar um `useRef` que mantém sempre o state mais recente, e usar esse ref no `save`:

**BEFORE (linhas 51-54 e 100-117):**
```typescript
export function useProductionState(channelId: string | undefined) {
  const { user } = useAuth();
  const [state, setState] = useState<ProductionState | null>(null);
  const [loading, setLoading] = useState(true);
  // ...
  const save = useCallback(async (updates: Partial<Omit<ProductionState, "channel_id">>) => {
    if (!channelId || !user) return;

    const merged: ProductionState = {
      ...(state ?? { channel_id: channelId, ...INITIAL }),
      // ...
    };
  }, [channelId, user, state]);
```

**AFTER:**
```typescript
export function useProductionState(channelId: string | undefined) {
  const { user } = useAuth();
  const [state, setState] = useState<ProductionState | null>(null);
  const stateRef = useRef<ProductionState | null>(null); // sempre aponta para o state mais recente
  const [loading, setLoading] = useState(true);

  // Manter o ref sincronizado com o state em cada render
  stateRef.current = state;
  // ...
  const save = useCallback(async (updates: Partial<Omit<ProductionState, "channel_id">>) => {
    if (!channelId || !user) return;

    // Usar stateRef.current em vez de state para evitar closure stale
    const currentState = stateRef.current;
    const merged: ProductionState = {
      ...(currentState ?? { channel_id: channelId, ...INITIAL }),
      ...updates,
      channel_id: channelId,
      data: { ...(currentState?.data ?? {}), ...(updates.data ?? {}) },
      updated_at: new Date().toISOString(),
    };

    setState(merged);
    stateRef.current = merged; // atualizar ref imediatamente para próximas chamadas síncronas

    await (supabase.from as any)("production_states").upsert(
      { ...merged, user_id: user.id },
      { onConflict: "channel_id" }
    );
  }, [channelId, user]); // state removido das deps — agora lemos via stateRef
```

Também adicionar `useRef` ao import do React no topo do arquivo:
```typescript
import { useState, useEffect, useCallback, useRef } from "react";
```

### Task 2: Distinguir erro de rede de "banco vazio" (BUG-014)

**Arquivo:** `src/hooks/useProductionState.ts`

**Localização:** linhas 60-73

**BEFORE:**
```typescript
const { data, error } = await (supabase.from as any)("production_states")
  .select("*")
  .eq("channel_id", channelId)
  .maybeSingle();

if (data && !error) {
  setState(data as ProductionState);
} else {
  setState({ channel_id: channelId, ...INITIAL });
}
```

**AFTER:**
```typescript
const { data, error } = await (supabase.from as any)("production_states")
  .select("*")
  .eq("channel_id", channelId)
  .maybeSingle();

if (error) {
  // Não resetar para INITIAL — pode haver estado válido no banco
  // Manter state como null = "não carregado" — UI deve mostrar reconnecting
  console.error("[useProductionState] Falha ao carregar estado do pipeline:", error.message);
  setState(null); // null = estado desconhecido, não = sem estado
} else if (data) {
  setState(data as ProductionState);
} else {
  // data === null && !error = banco confirmou que não há registro para este channelId
  setState({ channel_id: channelId, ...INITIAL });
}
```

## Risks

| Risco | Mitigação |
|-------|-----------|
| Remover `state` das deps do `useCallback` pode causar lint warning (exhaustive-deps) | Adicionar comentário `// eslint-disable-next-line react-hooks/exhaustive-deps` com justificativa explícita sobre o stateRef pattern |
| `stateRef.current = merged` imediatamente antes do await pode causar inconsistência se o upsert falhar | Aceito — o estado local fica atualizado mesmo que o banco falhe, mas isso é preferível ao stale closure |
| Threshold de 50 bytes pode aceitar blobs corrompidos | Blobs corrompidos têm tamanho variável — o critério de tamanho mínimo não detecta corrupção; isso é uma limitação conhecida e aceita |

## threat_model

| Threat | Category | Disposição |
|--------|----------|------------|
| Estado null exposto para a UI durante reconexão pode vazar informação de "está processando" | Information Disclosure | Accept — informação de baixo valor, visível apenas para o usuário autenticado |
| Chamadas consecutivas ao `save` sem serialização podem causar race condition no banco (dois upserts simultâneos) | Tampering | Accept — o Supabase `upsert` com `onConflict: "channel_id"` é idempotente; a última escrita vence |
