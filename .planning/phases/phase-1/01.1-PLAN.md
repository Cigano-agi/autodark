# Plan 1.1: Corrigir pipelineOrchestrator — Closure Stale, Error Handling e Auto-Resume

## Goal
O pipeline `runSemiAuto` executa do início ao fim sem travamento pós-visuals, persiste o step correto no catch, e o auto-resume detecta visuals não finalizados mesmo com lag do Realtime.

## Bugs Fixed
- **BUG-001** [critical] — Loop de polling lê `productionState?.scenes` de closure stale — nunca detecta que imagens foram geradas, sempre aguarda o timeout completo de 10s
- **BUG-002** [high] — Bloco `audio_upload` tem `catch {}` vazio — falha de upload mantém URL `blob:` que expira ao fechar a aba, sem nenhum log ou flag de re-upload
- **BUG-003** [critical] — `audio_url` no `persistStep` usa apenas `chaptersWithAudio[0]?.scenes[0]?.audioUrl` — placeholder nunca atualizado com as demais cenas
- **BUG-004** [high] — `catch` global lê `state.progress` de closure stale — persiste `step: 1` independente de onde o pipeline travou, impedindo auto-resume correto
- **BUG-005** [high] — Auto-resume verifica `hasUnfinishedVisuals(scenes)` antes do Realtime hidratar as cenas — pode não disparar quando recarrega durante geração visual

## Context

Este plano depende das correções dos planos 1.2, 1.3, 1.4 e 1.5 estarem aplicadas:
- Plan 1.2 muda o tipo de retorno de `generateAllNarrations` → `{ chapters, failedScenes }`
- Plan 1.3 corrige `extractScenes` para lançar erro explícito
- Plan 1.4 corrige `generateSEO` para não crashar
- Plan 1.5 corrige `useProductionState.save` para não ter closure stale

**Executar este plano POR ÚLTIMO entre os planos 1.x.**

### BUG-001 — Polling lê closure stale de productionState
`pipelineOrchestrator.ts:321-329`: o loop `while (waited < REALTIME_MAX_WAIT)` lê `productionState?.scenes` — mas `productionState` é capturado no closure de `runSemiAuto` no momento em que foi definido (primeiro render). React não atualiza closures stale. O valor de `productionState.scenes` dentro do loop é sempre o snapshot inicial (vazio ou desatualizado). Então `stillPending` nunca chega a zero via Realtime e o loop sempre aguarda os 10s completos.

Solução: usar um `useRef` que o `useEffect` do Realtime atualiza em tempo real.

### BUG-002 — catch vazio no audio_upload
`pipelineOrchestrator.ts:283-286`:
```typescript
} catch {
  // Upload de áudio falhou para esta cena; mantém URL local
}
```
Sem log, sem flag. Se o Storage falhar, o pipeline continua com `audioUrl: "blob:..."` que expira com a aba. Auto-resume não sabe que precisa re-fazer o upload.

### BUG-003 — audio_url com apenas a primeira cena
`pipelineOrchestrator.ts:292-295`: `audio_url: chaptersWithAudio[0]?.scenes[0]?.audioUrl || null`. Isso é código placeholder que nunca foi atualizado. O campo `audio_url` no banco fica com apenas a URL da primeira cena do primeiro capítulo.

### BUG-004 — step errado no catch global
`pipelineOrchestrator.ts:412`: `state.progress` é lido via closure stale. Mesmo que o pipeline tenha chegado ao step 4 (visuals prontos), se o erro ocorre ali, `state.progress` pode ser 0 ou um valor desatualizado. O auto-resume vai recomeçar do step errado.

### BUG-005 — Auto-resume com lag de Realtime
`pipelineOrchestrator.ts:86-102`: o `useEffect` verifica `hasUnfinishedVisuals(scenes)` imediatamente ao montar. Se o Realtime não hidratou as cenas ainda (lag de 500ms-2s é normal), `scenes` é `[]`, `hasUnfinishedVisuals([])` retorna false e o auto-resume nunca dispara.

useEffect(() => {
  if (!productionState) return;
  if (productionState.status !== "running") return;
  if (productionState.step !== 2.5) return;

  // Aguardar 2s para dar tempo ao Realtime de hidratar as cenas antes de verificar
  // Se scenes ainda vazio após 2s, o Realtime pode ter falhado — buscar do banco diretamente
  const timer = setTimeout(() => {
    const scenes = productionStateRef.current?.scenes ?? [];
    if (!hasUnfinishedVisuals(scenes)) {
      console.log("[orchestrator] Auto-resume: nenhuma cena pendente detectada após 2s — nada a retomar");
      return;

    console.log("[orchestrator] Auto-resume detectado — retomando worker de geração visual");
    runVisualWorker(channelId, (remaining) => {
      update({ message: `Auto-resume: imagens restantes: ${remaining}` });
    }).catch(err => {
      console.error("[orchestrator] Erro no auto-resume do worker:", err);
    });
  }, 2000); // 2s de delay para hidratação do Realtime

## Risks

| Risco | Mitigação |
|-------|-----------|
| `useRef` para productionState pode ter race condition com o useEffect do Realtime | O ref é atualizado no corpo da função (não em useEffect), então é síncrono com cada render — sem race condition |
| Delay de 2s no auto-resume pode ser lento para usuários com Realtime rápido | 2s é conservador; pode ser reduzido para 1s em iteração futura se o feedback for positivo |
| `audioUploadFailed: true` em SceneData requer mudança de tipo | Adicionar `audioUploadFailed?: boolean` em `src/agents/types.ts` — campo opcional, sem breaking change |
| `audio_urls_json` é nova coluna não existente no banco | O `persistStep` faz `update({ ...data })` — o Supabase vai ignorar campos não mapeados no schema. Verificar se a tabela `channel_contents` tem coluna `audio_urls_json`; se não, o dado é silenciosamente descartado (não causa crash) |

## threat_model

| Threat | Category | Disposição |
|--------|----------|------------|
| `errorMsg` do catch global incluído em `persistStep` como `error_log` — pode conter dados de API | Information Disclosure | Accept — `error_log` é coluna da tabela `channel_contents`, acessível apenas para o operador autenticado |
| Auto-resume disparado por Realtime pode executar múltiplas instâncias do worker em paralelo | Denial of Service | Mitigate — verificar se `runVisualWorker` já tem guard de "já em execução" antes de disparar o auto-resume; adicionar flag local se necessário |
